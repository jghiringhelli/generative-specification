## 1. Principles

1. **Present AND working.** An element counts only if it exists and a behavioural probe shows it does what it is for. A declared gate that was never run, a hook that is not installed in a fresh clone, a ratchet nobody reads, a lock that does not match: all `PARTIAL`. This answers the finding of the day-one census that declared gates had never been shown to block.
2. **Deterministic.** No model decides presence or working status. Two runs on the same repository give identical statuses and reasons (a test). Where a deterministic rule cannot decide (is the architecture document derived from the spec? is a criterion testable?), the checker tests a proxy and says it is a proxy; a different-vendor, twice-run model judge exists only as a flagged secondary instrument (FX-1 section 7) and never changes a status.
3. **Committed state only.** The repository under test is cloned; uncommitted files do not count and the repository is never modified (a test).
4. **Fresh clone, scrubbed environment.** Everything runs in a throwaway clone with no user git configuration and without inherited `npm_*`, `NODE_*` variables (a first run of the controls found that a child `node --test` inside a parent test run silently skips its files and reports success; the scrub fixes it and the controls guard it).
5. **One cause per probe, and a paired clean control for every probe.** A planted violation must be blockable only for the reason it represents, and a block counts only if the paired control (the same files and message style, minus the violation) is accepted: a hook that rejects all spec edits is not an open-questions gate, a script that fails at baseline is not a gate. Probes that touch source cite a requirement id and stage a doc change (never a spec or locked file) so the co-change gate cannot be the blocker (a first run found it crediting the test gate: control B05).
6. **Honest about leaks.** What the checker cannot see is listed (section 7) and has controls that pin the current behaviour so a reader knows exactly where it is blind.

## 2. Interface

`node checker.js --repo <path> [--config <file>] [--out <report.json>] [--only E01,E05] [--since <rev>] [--keep]`. Exit 0 only if all twelve are `PASS`. `--since` limits E09 to the commits after a boundary (the formula's first step). The report carries: checker version, SHA-256 of the configuration file, repository path and head, environment (node, git, platform), per item `status`, `reasons`, `evidence`, `subflags`, milliseconds, and a summary.

Status values: `PASS` present and working; `PARTIAL` present but not working or incomplete; `ABSENT` not present; `UNDETERMINABLE` the checker could not decide for an environmental reason (network failure on install or in a hook, a missing tool, a timeout, an exception). The registration forbids silent treatment of `UNDETERMINABLE` (FX-1 section 9.1).

Parameters (thresholds, regular expressions, candidate paths) live in `config.default.json`, hashed into every report and frozen with the registration. Changing one after freeze is a new checker version and triggers the re-scoring rule of FX-1 section 9.1.

## 3. The twelve items

Notation: "probe" = a violation or a clean change planted in the probe clone, followed by an attempt to commit, then (if not blocked) to push, then (if not blocked) the gate scripts. `blocked at commit` = the commit command exited non-zero and HEAD did not move; `at push` = a commit made with `--no-verify` was refused by the push to a fresh branch of a local bare remote; `at script` = a gate script that **passes on the clean head** (baseline-filtered) exits non-zero on the mutated tree. C0 is the baseline probe: a conventional, docs-only change to the README must be accepted (a plain message first, then one citing a requirement id if the plain one is refused; the accepted style is used afterwards); if C0 is blocked every probe-based item is `PARTIAL` with the reason "confounded by the baseline block", or `UNDETERMINABLE` when the block was a network failure.

## 4. The probe engine

A probe clone is prepared once per checked repository: `git clone --no-hardlinks`; install via the README's install-like commands (including hook installers and setup scripts), falling back to the stack default (`npm install`, `pip install`) if hooks are not active afterwards; the installed hooks are listed (`core.hooksPath` or `.git/hooks`). Between probes the clone is hard-reset to the checked head and cleaned (dependencies and lock files kept). A **commit attempt** applies the planted edits, stages exactly them, runs `git commit -m <message>`, and compares HEAD before and after. A **push attempt** commits with `--no-verify` and pushes to a fresh branch name of a local bare remote (so a pre-push gate is observable and pushes never collide). A **script probe** runs the allow-listed `package.json` scripts (names containing gate, check, lint, test, verify, lock, open, ratchet, cover, spec, sensor, guard, audit, valid; lifecycle scripts excluded) on the mutated tree, after computing which of them already fail on the clean head and excluding those. The same commit, push, script sequence applies to E05, E06, E07 and E10; E11 is commit-only.

Planted violations: a failing test (`tests/fx1_planted.test.js` that throws at load, `tests/test_fx1_planted.py` with `assert False`, or a failing statement appended to an existing test file); a syntax error appended to the source file that the tests import (config files, `setup.py`, `conftest.py` are never chosen); a conventional docs-only change (the clean change); an unattainable and a lowered ratchet floor; an open-question marker in a new trailing spec section and in an existing open-questions section, each with a marker-free twin; a source comment change with and without citation and doc change; an edit inside a locked spec section and an edit in an unlocked trailing section. All messages are conventional so a commit-message gate is never the unintended cause.

### 5.2 The dependency expectations (derived from element definitions)

A control removes or breaks one element; some others change as a logical consequence of the **element definitions**, not of how the control project is built. Only these couplings are logical: a missing or broken E01 breaks E04's routing; no E02 means nothing for E04's proxy, E07's marker, E08's criteria or E10's tags to refer to; no executed tests means E08's citations point at nothing; a baseline commit that is blocked makes every probe-based element (E05, E06, E07, E10, E11) uninformative (`PARTIAL`, confounded), and a failing test command also fails E12 when the README runs it. Couplings that exist only because the control project's gate script runs every check in one hook (a stale lock blocking all commits, hooks not installed removing the co-change rule) are **per-control expectations**, written in `variants.js` with a comment, not rules of the matrix.

Honest note on circularity: the first version of the expectations was written from this logic and then compared with the run; the first run disagreed three times (the environment leak, the unrelated-gate confound, and a fixture gate that crashed without a tests directory), all three were defects of the checker or the fixture, and all three were fixed and re-run. Several controls were then adjusted to fit (R05 also rewrites the ratchet floor). No outcome could have shown the expectations wrong once they were adjusted to the code, which is why the registered validation relies on independently authored controls and on the audit of model-written projects (5.3), not on this table.

## 6. Environment and safety

The checker executes code written by a model: README commands, install scripts, hooks, tests. It must run only in a disposable container: no credentials, no mounted home directory, network limited to the package registries (and any sources a hook framework needs, listed in the registration), a pinned image with Node 24, Python 3.11 with pytest, git, bash. The generating agent runs inside the same image (FX-1 section 3.3). Linux is the authority; the Windows prototype run is development only. Timeouts are in the configuration; a timeout is `UNDETERMINABLE`, not `PARTIAL`. The checker's own working folders live under the temp directory and are removed unless `--keep`.

## 7. Known leaks and risks (declared)

1. **Structural, not semantic.** E02 criteria of five words pass; E04 filler passes (L01); E03 records need headings, not reasoning. Two secondary model judges bound this and carry no verdict.
2. **E06 cannot tell a ratchet from a frozen file** (L02), nor verify that the measured quantity is meaningful; it requires that lowering the floor is rejected but cannot probe "a floor raised to the currently measured value is accepted" (the measured value is unknown to it).
3. **CI is never executed.** A repository enforcing only through CI gets `PARTIAL` on E05. Strict by design (a hook that blocks is observed, a workflow is not) and the largest difference between this checker and a user's idea of "gates"; the registered sensitivity analysis counts a statically valid CI workflow as a pass and reports both.
4. **Script credit.** E06, E07 and E10 credit a baseline-passing script that fails on the mutated tree, not only a hook (control X06). That is more lenient than "a hook blocks"; FX-1 registers the strict-enforcement sensitivity analysis. Script discovery reads `package.json` only, so python fixtures reach these elements by hook only (an asymmetry; Makefile and python entry points are not discovered).
5. **Convention dependence.** Folder names (English, with a first Spanish list), heading words (English and Spanish only), the id grammar (one or two letter groups and up to two numeric segments), the marker words, the lock format, the sentinel names and the slug rule are parameters fitted to the canon of the formulas. A repository using another convention for the same thing is scored down; the CHECKER-CONVENTION cause label (FX-1 section 9.3) routes such cases to the checker audit, not to the formula. Risk of understating success; measured by the audit.
6. **Stack coverage.** Node is exercised on most variants and python on two; other stacks are `UNDETERMINABLE` for E05. E05 and E11 plant into the source file that the tests import; a project with no test importing any source file falls back to the first source file.
7. **Probe confounds that remain.** A blocked commit is attributed to the probe because its paired control is accepted, but the checker does not read why it was blocked; the output tail is stored for human audit. A gate that blocks any commit that adds a file under `tests/` for an unrelated reason is mitigated by the fallback of appending to an existing test file, not eliminated.
8. **Install and README dependence.** A network failure is `UNDETERMINABLE`. A README whose setup is a script the checker cannot classify (`./go.sh`) leaves hooks uninstalled in the probe clone. A `console` block with unprefixed commands is not run. E12 runs commands one at a time with carried-over state lines only; long sessions (activating a virtual environment then running) work only through the carry-over of `source`, `export`, `cd`.
9. **Process hygiene.** A smoke-started server is killed as the direct child only; an orphan could survive in the same container. The checker therefore runs E12 last and the registration runs one container per repository.
10. **Probe shape.** The co-change probe is a comment-only change and the open-question marker is planted as a plain line; a gate scoped to behavioural changes or to the project's own section name would be scored down (a false fail).
11. **Goodhart.** The formulas and the checker are written by the same side and both are public; a formula may be tuned to the checker. FX-1 row (a) therefore says the claim is "met the FX-1 checker's definition".

## 8. Plugging into the SUBSTRATE-CHECKLIST (design)

The checklist is expected to give, per element, an id, a definition, and a way to check. The checker takes each of those as three adapters, all isolated in `lib/items.js` and `config.default.json`:

1. **Naming and layout**: the candidate paths, headings, id grammar, marker words and lock format become the checklist's. They are parameters, so a checklist change is a configuration change and a new checker version. If the checklist fixes the names, the candidate lists shrink to them and a deviation is a formula-following failure instead of a checker convention gap.
2. **Present predicate**: per element, a function of the repository (files and content patterns).
3. **Working probe**: per element, a list of (planted edit, paired control, expected outcome) triples that the probe engine runs. Where the checklist defines its own self-test ("break the gate on purpose and check in a fresh clone"), that self-test **is** the probe, executed by the checker rather than described.

Until the checklist exists, element ids E01 to E12 follow the order of the day-one definition. Mapping them to checklist ids is a freeze dependency (FX-1 section 13 item 2); where the checklist's definition of "working" is weaker or stronger than this one, one of them changes and the other is not allowed to differ silently.

The registration pins the commit, the file's SHA-256 and the configuration hash. Behavior of items E01 to E09 and E12 is unchanged from section 10; the control suite was ported as it was.
- **Strict enforcement (`--strict`, `--both`).** Default mode credits a failing package script (`npm run check`) as a gate; strict mode credits only a commit hook or a push hook that refuses a planted violation, because nothing runs a script unless a person does. In the dev loop, deleting the pre-push hook flagged only E05 on node projects: E06 and E07 were credited through the script. Controls `R06` and `GS2` pin the difference. The report carries `mode`. **Decision owed to JC before freeze:** register strict, default, or both. Recommended: strict as the registered mode, default reported as a sensitivity (the dev-loop report asked for the switch and both columns).
- **E10 (probe design fix).** The drift is a sentence written inside a tagged heading section; the twin (control) is a **new spec file**, never a trailing section appended to the same file (which could land inside a locked section, and made "any spec edit is a lock change" indistinguishable from a frozen spec). The static agreement of tags and lock entries now keys an entry by file, id and target. With the reference tool in the project, the checker also runs it: `check` clean, `check` after the drift (must exit non-zero and name STALE), `check` after the twin (must exit 0), `ratify` without a reason (refused, lock unchanged), with a reason (`check` passes and the record has the line), `commit-check` with and without the record. The tool's SHA-256 is compared with the copy next to the checker (informative, never a verdict).
- **E11 (refactor proof).** Added to the commit-time probes: a commit typed `refactor:` whose source breaks the parent's tests, with a test edited in the same commit, must be refused; a comment-only `refactor:` is the paired control. Both run with only the project's commit-msg hook active (an isolated hooks folder), so a failing test gate at pre-commit cannot be the cause. With the reference tool they are also given straight to `gs-cochange` (a proof that cannot run the project's tests is not credited). The hand-built gates of the known-good controls (`good`, `good-py`) gained the same proof; without it they would read PARTIAL, by design. A language other than JavaScript, TypeScript or Python gets no refactor probe (`refactor_probe` subflag).
- **`--only`** pulls in the items the chosen ones depend on (ids, cascade documents).
