## 1. Question, and what it is for

Capstone question: **on a medium project built from a complete specification and then changed repeatedly, does the GS bundle (the substrate: authored map, specification cascade with criterion ids, decision records, executed gates, ratchet, lock) change correctness, regression resistance or cost, compared with the same model given the same task without it, at two prompt qualities?**

It is an end-to-end test of the substrate, not of the method's other parts. It deliberately uses a **complete** specification: the effect of specification completeness (the dial) is a different experiment (section 13). It does not rank vendors, test human productivity, or test which component of the bundle acts (ablation is a later experiment).

Prior, stated as a prior and not a result: with a complete specification the bundle's gain in phase 1 is small (little to elicit, little to guess); its gain, if any, appears in phase 2, where the project changes and earlier rules must survive. Rival, equally plausible before data: a modern frontier model with a strong prompt and a good test habit reaches the same correctness at lower cost, so the substrate's value lies in governance, which this experiment does not measure.

## 2. Design

Four arms, crossing two factors. Every arm uses the same model, the same specification text, the same tool set and the same limits; arms differ only in the two factors.

| Arm | Prompt factor | Substrate factor | What the session receives |
|---|---|---|---|
| N (naive) | naive: the task statement only | absent | the specification file and the task text (SDX-1-ARMS A0) |
| N+S | naive | present | the same task text; the repository already holds the installed substrate |
| X (expert, no GS) | expert, written by an external practitioner | absent | task text plus the practitioner's prompt, with no bridge, no phase collapse and none of the other load-bearing elements (leak-checked); tests and similar generic practice allowed |
| X+S | expert (byte-identical to X) | present | X plus the installed substrate |

Rules that keep the 2x2 honest:
1. **User text is identical across the bundle factor.** N+S uses N's task text byte for byte; X+S uses X's prompt byte for byte. The second factor is called the **GS bundle** (present or absent): persistent, routed, enforced material in the repository, **including the instructions it auto-loads**, which a model reads in every session and which therefore act as a second prompt (critic finding). The 2x2 consequently crosses "user text quality" with "bundle present", not "prompt" with "non-prompt". Whether the gain comes from the bundle's persistence and enforcement or from its auto-loaded text is not separated here; the arm that would separate it (the same content flattened into one file, SDX-1 A3, as X+F) is an optional fifth arm, default not added, and P4 and SDX-1 are where that contrast belongs. Rows (g) to (i) of the decision table are worded accordingly.
2. **Arm X is the practitioner's natural expert prompt** (SDX-1-ARMS A6 procedure: external practitioner with no GS exposure, attestation, hash, strength check M2), not the persistence-stripped A5. "No bridge, no phase collapse" is secured by the practitioner's independence and brief, not by filtering the text afterwards. The leak classification M1 is **descriptive only** for X, as it was for A6 in SDX-1: whatever persistence or verification habits the practitioner includes are the arm. Reason: for an end-to-end capstone the fair rival lets the expert keep tests, README and notes. Whatever bundle the arm builds by itself is counted by the emergent-substrate detector and reported as a mediator; if the expert prompt induces much of a substrate, the X+S minus X contrast shrinks, which is a valid result and is worded as such. The practitioner sees the specification and the project description and **never the change list, traps, oracle or any GS material**; the bundle builder likewise never sees the traps. Declared: the GS side has seen the P4 trap classes and wrote the conformance checker. The persistence-stripped A5 can be added as a fifth arm; default: not added.
3. **Substrate setup** is done once per project by the GS side with the canonical formula, from the specification only, by a builder who has not seen any phase 2 change request or trap. The result must pass the conformance checker (all twelve elements present and working, FX-1 checker) and is hashed before runs. Setup hours and tokens are recorded and enter the cost outcome (section 6).
4. **Equal tooling and budgets.** Same tools in every arm (read, edit, shell, git, test runner); web and MCP disabled; same per-session and per-run token and wall-clock caps `[FROM E2E-0]`; hooks exist only where the arm's repository has them. A substrate arm spends part of the same budget on upkeep; that is the point of counting cost per accepted change.
5. **Scored state and blocked commits.** The scored state is the last tree state when the session stops on its own or hits the cap, whatever hooks did; a session that ends with a blocked, uncommitted tree is scored as that tree. Hook blocks, retries inside a session and gate overrides are counted per arm as mediators, because they are in-session work that arms without hooks do not have.
6. **Fresh session for every step**, fresh configuration directory, memory off, unique repository path, only the repository carries state (as SDX-1 section 3; harness persistence checked by the planted-memory test).

## 3. Projects (units of replication)

Two invented medium projects (plan: 10 to 20 kLOC when built, 30 to 40 use cases, each with a criterion id and acceptance criteria; a data store, an authentication and role model, at least one background or scheduled behaviour, at least one reporting query, one migration-sensitive data model). Written by a person who does not design the substrate; **project 2 is written and its traps chosen by someone who doubts GS**, with the GS side holding a logged veto only for ambiguity. Invented domains; a cold canary run per model before use (recall above zero is INVALID-DESIGN for that model). Reuse of Pastura machinery (locked scaffold, sealed convention-tolerant oracle, canary, arms) and of the P4 trap pipeline, not of Pastura itself, except that project 1 may be built on the P4 base repository family if P4 has been run (shared fixture, cited as one fixture). Each trap is classified before freezing by whether its rule is stated in the specification text (visible to every arm) or is implicit in the code; P-REG is reported by class. The skeptic's traps are frozen and hashed before the GS side sees them; the GS side's veto log goes to the independent reviewer. Three projects instead of two is the funded upgrade (section 9).

## 4. Phases

**Phase 1, build.** The complete specification is given to every arm in the same form (a file in the working directory at the start). The build is split into `[8 to 10]` increments, each a fresh session that sees only the repository; this is what gives persistence something to do. A one-session full build is not used: AX and AX2 are single-shot and saturated. Declared: bundle arms start from a substrate whose cascade was generated from the specification, so they begin with pre-decomposed spec work that the other arms lack; that is part of the treatment and its cost is counted (section 6), but it changes what phase 1 measures.

**Phase 2, change.** A scripted list of `[12 to 16]` change requests per project, each a fresh session: `[8 to 10]` **planted traps** (the natural implementation breaks a rule or invariant carried since phase 1; authored independently and frozen before any run), 2 specification changes that supersede earlier behaviour, 1 reversal of an earlier feature, and 2 plain features as position controls. The traps are the headroom (section 8). Scored state is the working tree after the last attempt of each step; retry rule identical across arms and never conditioned on the arm's own test results.

## 5. Models

Three vendors (three different companies), one modern frontier model each, dated snapshot ids, CLI and runtime versions pinned and logged, all runs in a short window, arm order randomized in blocks with vendor interleaved. Open: run each vendor in its own CLI (convenient, but vendor and harness become one factor) or in one neutral minimal harness with the same tools for all (cleaner, costs build time); default: the neutral harness; own CLIs are allowed only with a registered, reviewed per-vendor port of the auto-loaded file names and loading rules (a port is not byte-identical) and the confound declared; failing to validate the neutral harness in E2E-0 is reported, not hidden. Judges and reviewers are always from a vendor other than the generator of the run being judged (section 7).

## 6. Outcomes

**Co-primary (alpha 0.025 each, 97.5% intervals):**
- **P-ACC**: share of sealed hidden acceptance probes passed at the end of phase 2 (all use cases, fresh and carried). Sealed outside every repository, written before any run from the specification only, convention-tolerant (status-class tolerance plus value checks), validated with a reference implementation, stubs and mutants; never visible to any arm or used to tune any arm.
- **P-REG**: share of trap steps in which no carried probe regressed (held-out probes, not the gate's visible suite). A trap counts for a run only if the carried behaviour it endangers passed at its own earlier step (otherwise the regression is vacuous); excluded traps are reported per arm and an intention-to-treat version (excluded counts as failure) is a registered sensitivity. With `[8 to 10]` traps per run, binomial noise alone is about 15 points, so the run-level SD of P-REG is expected to be larger than that of P-ACC `[FROM E2E-0]`.

**Co-secondary, with verdict power only in row (e) of the decision table:** tokens and dollars per accepted change over the whole run, **including substrate setup (amortized over the phase 2 length, and shown unamortized) and upkeep**, with every human intervention logged per arm (setup, prompt authoring, ratification, lock or baseline decisions, fixing conformance failures) and valued at one rate `[AT FREEZE]`, reported with and without human time and at three amortization horizons (12, 100 and 1,000 changes) with **no verdict on the horizon**. The ratio of cost per accepted change is analysed as a ratio with a 95% interval.

**Secondary (95% intervals, no multiplicity adjustment, worded "suggests", no verdict except as stated):** phase 1 acceptance (reported as ceiling check, section 8); interaction; prompt main effect; simple effects X+S minus X and N+S minus N; per vendor results (descriptive); static analysis with a **frozen profile that no arm's prompt or substrate refers to** (independent default ruleset for warnings, complexity, duplication, dependency audit); failures and retries per arm; emergent-substrate counts; gate false-blocks, circumvention events (test deletion or weakening, hook edits, baseline edits) per arm; session count and wall-clock.

**Judged outcomes (secondary):** blind pairwise judgments of maintainability and spec-conformance by two judges from the two vendors other than the generator, calibrated first on planted defects (BACKLOG B11); a judge that fails calibration is replaced or the judged outcome is declared unevaluable. Judges receive the source tree with the bundle's paths stripped, so arm identity is not visible from the substrate (traces in naming and comments remain, and this is stated).

**The seven-property rubric (SAVED, Bounded, Composable and so on) is secondary and circular.** It is the treatment's own vocabulary; its calibration on 10 targets reached pairwise exact agreement .64 with replicates of one model, and this experiment must not rest on it. It is reported descriptively, never used as a verdict or as a selection criterion.

## 7. Human checks and blinding

Use cases are checked by a person on the **running system**, through a neutral interface and neutral identifiers, in randomized order. It is a sample, not the oracle: a third of the runs (stratified by arm and vendor, registered seed), `[10]` use cases per run drawn by the seed. A **second checker who is not a GS person does the primary pass on the sample; JC does a second pass** on a third of it and on the full sample if time allows; agreement is reported. The set of use cases where the acceptance suite and a judge disagree is drawn by an assistant after the first pass and shown to the checkers only then. Scoring: pass, fail, unclear, with a note, against criterion text fixed in advance. Purposes: estimate the acceptance suite's false-pass rate and find defects it misses (those feed HR-1). Limits stated: JC knows the method and has a stake; black-box checking hides repository artifacts but not every trace (response wording, logging), so blinding is nominal, and a blinding-guess test (each checker guesses the arm after each run) is registered. Disagreement between a checker and the suite never changes the suite after freeze; it is reported.

## 8. Ceiling, floor, controls, validity triggers

- **Ceiling.** A complete specification on a medium project with frontier models will probably saturate phase 1 (AX2 and MX did). Phase 1 is therefore a ceiling and floor check, not a verdict outcome; headroom comes from phase 2. Pilot E2E-0 (one project, one vendor, all four arms, 1 run each, excluded from analysis) must show headroom: if the weaker arm of the primary contrast is at or above 100 minus the SESOI (92% on P-ACC, 90% on P-REG) there is no room for the effect, so harder traps are added before freezing, **chosen using arm N only (the floor arm), never the contrast**, and every trap change is logged; if no headroom can be built, the experiment is declared not worth running. One run per arm cannot give an SD or a headroom decision with confidence: E2E-0 is one project, one vendor, four arms times three runs (12 runs) and its SD is treated as a rough guide (the interval is wide).
- **Positive control.** A step with a known effect: a trap whose rule is stated in the change text of one extra arm (not part of the 2x2, `[5]` runs) must be avoided at least `[90]`% of the time or the trap measure does not work. E2E-0 and both controls are counted in the cost and in the run total (section 9).
- **Negative control.** A duplicated run of arm X (X-b) per vendor and project, to estimate run-to-run noise on both co-primaries; if the difference X minus X-b is as large as the SESOI with an interval excluding zero, noise exceeds the effect: INVALID-DESIGN.
- **Manipulation checks.** Leak check on arm X (none of the named elements), parity of artifact sizes reported (not forced equal), conformance checker pass on the substrate, emergent-substrate detector on all runs.
- **INVALID-DESIGN triggers:** canary recall above zero; harness persistence found; acceptance suite fails reference or mutant validation; differential cap-hits above `[10]` points; practitioner independence broken (arm X); bundle fails the checker; no phase 2 headroom (row v); model, CLI or runtime changed mid-window; both factors confounded by an authoring asymmetry found by the independent reviewer.

## 9. Sample size, power and cost (assumptions, not results)

Unit of analysis: the **run** (items inside a run are not independent). Planning: 4 arms x 3 vendors x 2 projects x 3 repetitions = **72 runs**, 18 per arm, 6 per cell (arm by vendor); the per-vendor bundle contrast is 12 runs versus 12. Controls and pilot add `[X-b: 6 runs, positive control: 5 runs, E2E-0: 12 runs]` = 23 runs, so about 95 in all. Funded upgrade: 3 projects x 4 repetitions = 144 runs, 36 per arm. **The runs are fewer independent units than they look:** each project has one bundle build, one expert prompt and one trap list, and there are two projects, so inference is conditional on these projects and does not extend to a population of projects; three projects is the minimum for even a rough statement about that.

By formula with run-level SD 12 points (assumption; the earlier simulations use 8 to 15), 97.5% interval, 80% power: substrate main effect (36 versus 36 runs) detects about 8.7 points (10.9 at SD 15); a simple effect such as X+S minus X (18 versus 18) about 12 points; the **interaction about 17 points** (twice the standard error of a main effect). At 144 runs the main effect is about 6 points. Power at the SESOI itself (8 points, SD 12) is about 0.7 for the main effect and about 0.4 for a simple effect, not 0.8. SD sensitivity of the main-effect detectable gap: 7.3 / 8.7 / 10.9 points at SD 10 / 12 / 15 (normal quantiles; t quantiles with few strata widen these by roughly 5 to 10%). The SD is borrowed from single-shot and chain experiments, not from this design `[FROM E2E-0]`. Equivalence: with margin 8 the main effect can be called EQUIVALENT only if the 97.5% half-width (about 6.3 at SD 12) fits inside it; simple effects (half-width about 9) **cannot** be labelled EQUIVALENT at this n and are reported as unresolved or with their interval. Per-vendor estimates are descriptive only: no vendor-specific claim is made.

Reading of the picture, in the portfolio's own terms: at 72 runs the design resolves a bundle effect of about 9 points or more and stays **inconclusive for a gap of about 6 points or less**; the interaction is resolved only if it is large. A single build per arm (12 runs) is a **demonstration (tier D), not a rate**; the pilot E2E-0 is exactly that and is excluded. Earlier results leave doubt whether the gap exists at this model class (AX2 saturated; the SDX-1 central gap of 9 points with SD 10 to 15 gave an inconclusive probability of 0.28 to 0.67 at n=20). JC's rule (run nothing whose probable result is inconclusive) is a decision for him; this draft states the probability instead of hiding it.

Cost (model only, guesses until E2E-0 measures them): about 25 to 31 sessions per run, `$0.8 to $3.0` per frontier session at this scale, so about `$25 to $95` per run: 72 runs about `$1.8k to $6.8k` (about 95 runs with controls and pilot, `$2.4k to $9k`); 144 runs plus controls about `$4.2k to $15.5k`; judges and extra reviews about 10 to 15% more. Preparation (specifications, acceptance suites, traps, substrates, practitioner, independent reviewer) is the larger cost: a guess of `[120 to 200]` agent-assisted hours per project, plus paid independent persons. JC's time for section 7: about 12 to 20 hours.

## 10. Analysis plan, exactly as registered

1. Controls, manipulation checks and INVALID-DESIGN triggers before any contrast.
2. Co-primary: the bundle main effect (N+S and X+S versus N and X) on P-ACC and P-REG as a risk difference in points at the run level, by a **stratified permutation test and interval** (runs exchangeable within project x vendor strata, 100,000 permutations, seed registered); cluster-robust errors are not used (two clusters). The same contrast is also reported on the logit scale, and the interaction on both scales, because an interaction on a bounded share near the ceiling depends on the scale. Classification as in SDX-1 section 2.2 with the SESOI `[8]` points on P-ACC and `[10]` on P-REG (provisional, justified at freeze).
3. Secondary, labelled: interaction, prompt main effect, simple effects, cost rows, static analysis, judged outcomes, per vendor table, rubric (descriptive).
4. Heterogeneity: the bundle estimate and interval in each of the three vendors, and a bundle-by-vendor interaction estimate. A result is worded "across vendors" only if the three estimates point the same way and the heterogeneity estimate is small relative to the main effect; otherwise "mixed". (Three equal signs occur 25% of the time under a true null, so the sign count alone is not used.)
5. Exploratory, no verdict: failure taxonomy of phase 2 regressions; escapes of the automated checks (feeds HR-1).
6. No stopping rule beyond the fixed n; one interim validity look by a script that prints flags only.

## 11. Decision table (registered)

Precedence: (v) first; then (d); then (a) to (c) and (f) by the pair of co-primary classes below; (e) is assessed on every row where quality is not REVERSED; (g) to (l) are secondary or audit rows and never override a primary row. Each co-primary gets one class (POSITIVE with its size class, EQUIVALENT, REVERSED, INCONCLUSIVE) from SDX-1 section 2.2; "positive-small" means L > 0 and U <= SESOI. Every pair of classes is assigned to exactly one row:

| Row | Pair of co-primary classes (P-ACC, P-REG) | Permitted conclusion (these projects, vendors, snapshots, complete specification) | Forbidden |
|---|---|---|---|
| (v) INVALID | any trigger in section 8, including no headroom in phase 2 | INVALID-DESIGN naming the trigger; linked redesign | any conclusion, including reading it as a null |
| (d) **GS loses on quality** | either is REVERSED (REVERSED-RELEVANT if the point estimate is at or below minus the SESOI) | friction, upkeep or gate side effects cost more than they bought here; reported prominently | rescue by post-hoc subgroup |
| (a) | both POSITIVE | the bundle improved acceptance and regression resistance at these conditions; sizes, intervals, per-vendor table | "GS multiplies productivity"; which component acts; other domains or sizes; later models |
| (b) | one POSITIVE, the other EQUIVALENT | the bundle changed only the positive outcome (for example protected against regression, final acceptance unchanged) | claiming an effect on the equivalent outcome |
| (b2) | one POSITIVE, the other INCONCLUSIVE | the bundle improved one outcome; the other is unresolved at this n | any statement on the unresolved one |
| (c) | both EQUIVALENT | **no measurable difference in correctness here**; any value lies in what was not measured (governance, continuity, audit, cost of future change); row (e) then decides the cost reading | "GS is useless"; rescue by regimes outside 10a |

| Row | Observed | Permitted wording |
|---|---|---|
| (g) | interaction positive on both scales (bundle gain larger with the naive user text) | the bundle's gain is larger when user text is weak; the gain over an expert prompt (simple effect X+S minus X, with its interval) is smaller; this does not show that the bundle replaces expertise |

**10a. Regimes registered as untested (the only ones that may be named after rows c, d or e):** specification completeness below complete (the dial, section 13); repositories larger than the medium projects; multiple contributors or people; humans in the loop beyond the sampled checks; governance and audit outcomes; models older or newer than the pinned snapshots; project domains other than the two.

Claims the result could support: for the pinned frontier models and these two invented medium projects with a complete specification, conditional on these projects, the size and direction of the bundle's effect on final acceptance, regression resistance and cost per accepted change, relative to the same prompt quality without it, with an interval, plus a descriptive per-vendor table and a list of the defects the automated nets missed. Claims it cannot support: human productivity, speed, maintainability for people, which component acts, results on incomplete specifications, other sizes, other domains, future models, or that a disciplined human expert with full practice would not match the bundle.

## 12. Threats to validity (declared)

Proponent-authored substrate, sensors, change list and some oracle parts (mitigations: external practitioner and independent reviewer, skeptic-chosen second project and traps, builder blind to phase 2, sealed oracle validated before runs, judges from other vendors). The "prompt" factor is per-session text only; the substrate also contains instructions, so the 2x2 separates delivery and persistence, not content from non-content. The bundle is tested as a whole. Small n of independent units (18 runs per arm). Two invented projects. Frontier-model snapshots are dated and will be replaced. Vendor and harness are confounded if own CLIs are used. The judged and human outcomes are secondary because of reviewer stake. A complete specification favours the substrate's cascade (little to elicit) and also the naive arms (little to guess): the net direction is not known.

## 13. The separate later experiment: specification completeness (the dial) — not part of E2E-1

One project, the substrate factor kept as in E2E-1 (X versus X+S only), crossed with specification completeness at four levels: one-paragraph intent; intent plus principal rules; criteria for the main flows; complete (E2E-1's specification). The hidden acceptance suite stays complete at every level and is written from the complete specification, with a registered list of the decisions each lower level leaves open. Outcomes: acceptance pass on the complete suite; the assumptions the agent recorded or asked about; defects traceable to an unstated decision. Prediction to test: the substrate's value rises as completeness falls (it forces recording decisions) or falls (it multiplies guesses); the sign is unknown. AX cannot answer it: it varied completeness together with GS content and method in one session each, its upper levels saturated, its later versions were iterated with knowledge of the gaps (demonstration), and its rubric is the treatment's own.
