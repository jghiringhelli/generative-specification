## 1. Question, and what it is for

Capstone question: **on a medium project built from a complete specification and then changed repeatedly, does the GS bundle (the substrate: authored map, specification cascade with criterion ids, decision records, executed gates, ratchet, lock) change correctness, regression resistance or cost, compared with the same model given the same task without it, at two prompt qualities?**

It is an end-to-end test of the substrate, not of the method's other parts. It deliberately uses a **complete** specification: the effect of specification completeness (the dial) is a different experiment (section 13). It does not rank vendors, test human productivity, or test which component of the bundle acts (ablation is a later experiment).

Prior, stated as a prior and not a result: the substrate keeps a changing project correct and cheap to change, independent of the prompt. Rival, equally plausible before data: a modern frontier model with a strong prompt and a good test habit reaches the same correctness at lower cost, so the substrate's value lies in governance, which this experiment does not measure.

## 2. Design

Four arms, crossing two factors. Every arm uses the same model, the same specification text, the same tool set and the same limits; arms differ only in the two factors.

| Arm | Prompt factor | Substrate factor | What the session receives |
|---|---|---|---|
| N (naive) | naive: the task statement only | absent | the specification file and the task text (SDX-1-ARMS A0) |
| N+S | naive | present | the same task text; the repository already holds the installed substrate |
| X (expert, no GS) | expert, written by an external practitioner | absent | task text plus the practitioner's prompt, with no bridge, no phase collapse and none of the other load-bearing elements (leak-checked); tests and similar generic practice allowed |
| X+S | expert (byte-identical to X) | present | X plus the installed substrate |

Rules that keep the 2x2 honest:
1. **Prompt text is identical across the substrate factor.** N+S uses N's task text byte for byte; X+S uses X's prompt byte for byte. The substrate may carry instructions (an auto-loaded file); that is the substrate, not the prompt, and is declared as part of the bundle. The factor labelled "prompt" is therefore "per-session text supplied by the user", the factor "substrate" is "persistent, routed, enforced material in the repository". This split is declared as a limit (section 12), not hidden.
2. **Arm X is the practitioner's natural expert prompt** (SDX-1-ARMS A6 procedure: external practitioner, no GS exposure, attestation, hash, leak check M1 against the named elements, strength check M2), not the persistence-stripped A5. Reason: for an end-to-end capstone the fair rival lets the expert keep tests, README and notes. Whatever substrate the arm creates by itself is counted by the emergent-substrate detector and reported as a mediator. The A5 variant (persistence forbidden) can be added as a fifth arm if JC wants the cleaner isolation; default: not added.
3. **Substrate setup** is done once per project by the GS side with the canonical formula, from the specification only, by a builder who has not seen any phase 2 change request or trap. The result must pass the conformance checker (all twelve elements present and working, FX-1 checker) and is hashed before runs. Setup hours and tokens are recorded and enter the cost outcome (section 6).
4. **Equal tooling and budgets.** Same tools in every arm (read, edit, shell, git, test runner); web and MCP disabled; same per-session and per-run token and wall-clock caps `[FROM E2E-0]`; hooks exist only where the arm's repository has them. A substrate arm spends part of the same budget on upkeep; that is the point of counting cost per accepted change.
5. **Fresh session for every step**, fresh configuration directory, memory off, unique repository path, only the repository carries state (as SDX-1 section 3; harness persistence checked by the planted-memory test).

## 3. Projects (units of replication)

Two invented medium projects (plan: 10 to 20 kLOC when built, 30 to 40 use cases, each with a criterion id and acceptance criteria; a data store, an authentication and role model, at least one background or scheduled behaviour, at least one reporting query, one migration-sensitive data model). Written by a person who does not design the substrate; **project 2 is written and its traps chosen by someone who doubts GS**, with the GS side holding a logged veto only for ambiguity. Invented domains; a cold canary run per model before use (recall above zero is INVALID-DESIGN for that model). Reuse of Pastura machinery (locked scaffold, sealed convention-tolerant oracle, canary, arms) and of the P4 trap pipeline, not of Pastura itself, except that project 1 may be built on the P4 base repository family if P4 has been run (shared fixture, cited as one fixture). Three projects instead of two is the funded upgrade (section 9).

## 4. Phases

**Phase 1, build.** The complete specification is given to every arm in the same form (a file in the working directory at the start). The build is split into `[8 to 10]` increments, each a fresh session that sees only the repository; this is what gives persistence something to do. A one-session full build is not used: AX and AX2 are single-shot and saturated.

**Phase 2, change.** A scripted list of `[12 to 16]` change requests per project, each a fresh session: `[8 to 10]` **planted traps** (the natural implementation breaks a rule or invariant carried since phase 1; authored independently and frozen before any run), 2 specification changes that supersede earlier behaviour, 1 reversal of an earlier feature, and 2 plain features as position controls. The traps are the headroom (section 8). Scored state is the working tree after the last attempt of each step; retry rule identical across arms and never conditioned on the arm's own test results.

## 5. Models

Three vendors (three different companies), one modern frontier model each, dated snapshot ids, CLI and runtime versions pinned and logged, all runs in a short window, arm order randomized in blocks with vendor interleaved. Open: run each vendor in its own CLI (convenient, but vendor and harness become one factor) or in one neutral minimal harness with the same tools for all (cleaner, costs build time); default: neutral harness if it can be built and validated in E2E-0, otherwise own CLIs with the confound declared. Judges and reviewers are always from a vendor other than the generator of the run being judged (section 7).

## 6. Outcomes

**Co-primary (alpha 0.025 each, 97.5% intervals):**
- **P-ACC**: share of sealed hidden acceptance probes passed at the end of phase 2 (all use cases, fresh and carried). Sealed outside every repository, written before any run from the specification only, convention-tolerant (status-class tolerance plus value checks), validated with a reference implementation, stubs and mutants; never visible to any arm or used to tune any arm.
- **P-REG**: share of trap steps in which no carried probe regressed (held-out probes, not the gate's visible suite).

**Co-secondary, with verdict power only in the cost rows of the decision table:** tokens and dollars per accepted change over the whole run, **including substrate setup (amortized over the phase 2 length, and shown unamortized) and upkeep**, with human hours (setup, prompt authoring) valued at one stated rate and reported with and without them.

**Secondary (no verdict):** phase 1 acceptance (reported as ceiling check, section 8); interaction; prompt main effect; simple effects X+S minus X and N+S minus N; per vendor results (descriptive); static analysis with a **frozen profile that no arm's prompt or substrate refers to** (independent default ruleset for warnings, complexity, duplication, dependency audit); failures and retries per arm; emergent-substrate counts; gate false-blocks, circumvention events (test deletion or weakening, hook edits, baseline edits) per arm; session count and wall-clock.

**Judged outcomes (secondary):** blind pairwise judgments of maintainability and spec-conformance by two judges from the two vendors other than the generator, calibrated first on planted defects (BACKLOG B11); a judge that fails calibration is replaced or the judged outcome is declared unevaluable.

**The seven-property rubric (SAVED, Bounded, Composable and so on) is secondary and circular.** It is the treatment's own vocabulary; its calibration on 10 targets reached pairwise exact agreement .64 with replicates of one model, and this experiment must not rest on it. It is reported descriptively, never used as a verdict or as a selection criterion.

## 7. Human checks and blinding

JC checks use cases himself, on the **running system**, through a neutral interface and neutral identifiers, in randomized order, before he sees any automated result. It is a sample, not the oracle: per run drawn into the sample (a third of the runs, stratified by arm and vendor, chosen by a registered seed), `[10]` use cases drawn by the seed plus every use case where the acceptance suite and a judge disagree. Scoring: pass, fail, unclear, with a note, against criterion text fixed in advance. Purposes: estimate the acceptance suite's false-pass rate and find defects it misses (those feed HR-1). Limits stated: JC knows the method and has a stake; black-box checking hides repository artifacts but not every trace (response wording, logging); a second checker who is not a GS person repeats a fifth of the sample for agreement. Disagreement between JC and the suite never changes the suite after freeze; it is reported.

## 8. Ceiling, floor, controls, validity triggers

- **Ceiling.** A complete specification on a medium project with frontier models will probably saturate phase 1 (AX2 and MX did). Phase 1 is therefore a ceiling and floor check, not a verdict outcome; headroom comes from phase 2. Pilot E2E-0 (one project, one vendor, all four arms, 1 run each, excluded from analysis) must show headroom: if the weaker arm of the primary contrast is at or above `[95]`% on P-ACC and P-REG, add harder traps before freezing; if no headroom can be built, the experiment is declared not worth running.
- **Positive control.** A step with a known effect: a trap whose rule is stated in the change text of one extra arm (not part of the 2x2, `[5]` runs) must be avoided at least `[90]`% of the time or the trap measure does not work.
- **Negative control.** A duplicated run of arm X (X-b) per vendor and project, to estimate run-to-run noise on both co-primaries; if the difference X minus X-b is as large as the SESOI with an interval excluding zero, noise exceeds the effect: INVALID-DESIGN.
- **Manipulation checks.** Leak check on arm X (none of the named elements), parity of artifact sizes reported (not forced equal), conformance checker pass on the substrate, emergent-substrate detector on all runs.
- **INVALID-DESIGN triggers:** canary recall above zero; harness persistence found; acceptance suite fails reference or mutant validation; differential cap-hits above `[10]` points; leak in arm X; substrate fails the checker; model, CLI or runtime changed mid-window; both factors confounded by an authoring asymmetry found by the independent reviewer.

## 9. Sample size, power and cost (assumptions, not results)

Unit of analysis: the **run** (items inside a run are not independent). Planning: 4 arms x 3 vendors x 2 projects x 3 repetitions = **72 runs**, 18 per arm, 6 per cell (arm by vendor). Funded upgrade: 3 projects x 4 repetitions = 144 runs, 36 per arm.

By formula with run-level SD 12 points (assumption; the earlier simulations use 8 to 15), 97.5% interval, 80% power: substrate main effect (36 versus 36 runs) detects about 8.7 points (10.9 at SD 15); a simple effect such as X+S minus X (18 versus 18) about 12 points; the **interaction about 17 points** (twice the standard error of a main effect). At 144 runs the main effect is about 6 points. Per-vendor cells (6 runs) are descriptive only: no vendor-specific claim is made.

Reading of the picture, in the portfolio's own terms: at 72 runs the design resolves a large substrate effect and stays **inconclusive for a gap of about 5 points or less**; the interaction is resolved only if it is large. A single build per arm (12 runs) is a **demonstration (tier D), not a rate**; the pilot E2E-0 is exactly that and is excluded. Earlier results leave doubt whether the gap exists at this model class (AX2 saturated; the SDX-1 central gap of 9 points with SD 10 to 15 gave an inconclusive probability of 0.28 to 0.67 at n=20). JC's rule (run nothing whose probable result is inconclusive) is a decision for him; this draft states the probability instead of hiding it.

Cost (model only, guesses until E2E-0 measures them): about 25 to 31 sessions per run, `$0.8 to $3.0` per frontier session at this scale, so about `$25 to $95` per run: 72 runs about `$1.8k to $6.8k`; 144 runs about `$3.6k to $13.7k`; judges and extra reviews about 10 to 15% more. Preparation (specifications, acceptance suites, traps, substrates, practitioner, independent reviewer) is the larger cost: a guess of `[120 to 200]` agent-assisted hours per project, plus paid independent persons. JC's time for section 7: about 12 to 20 hours.

2. Co-primary: the substrate main effect (N+S and X+S versus N and X) on P-ACC and P-REG at the run level, adjusted for project and vendor (fixed effects; cluster-robust or permutation interval at the run level; seed registered). Classification as in SDX-1 section 2.2 with the SESOI `[8]` points on P-ACC and `[10]` on P-REG (provisional, justified at freeze).
3. Secondary, labelled: interaction, prompt main effect, simple effects, cost rows, static analysis, judged outcomes, per vendor table, rubric (descriptive).
4. Heterogeneity: sign of the substrate effect in each of the three vendors reported; a result is worded "across vendors" only if the sign agrees in all three and no vendor is equivalent; otherwise "mixed".
5. Exploratory, no verdict: failure taxonomy of phase 2 regressions; escapes of the automated checks (feeds HR-1).
6. No stopping rule beyond the fixed n; one interim validity look by a script that prints flags only.

**10a. Regimes registered as untested (the only ones that may be named after rows c, d or e):** specification completeness below complete (the dial, section 13); repositories larger than the medium projects; multiple contributors or people; humans in the loop beyond the sampled checks; governance and audit outcomes; models older or newer than the pinned snapshots; project domains other than the two.

Claims the result could support: for the pinned frontier models and these two invented medium projects with a complete specification, the size and direction of the bundle's effect on final acceptance, regression resistance and cost per accepted change, relative to the same prompt quality without it, with an interval, plus a descriptive per-vendor table and a list of the defects the automated nets missed. Claims it cannot support: human productivity, speed, maintainability for people, which component acts, results on incomplete specifications, other sizes, other domains, future models, or that a disciplined human expert with full practice would not match the bundle.

## 12. Threats to validity (declared)

Proponent-authored substrate, sensors, change list and some oracle parts (mitigations: external practitioner and independent reviewer, skeptic-chosen second project and traps, builder blind to phase 2, sealed oracle validated before runs, judges from other vendors). The "prompt" factor is per-session text only; the substrate also contains instructions, so the 2x2 separates delivery and persistence, not content from non-content. The bundle is tested as a whole. Small n of independent units (18 runs per arm). Two invented projects. Frontier-model snapshots are dated and will be replaced. Vendor and harness are confounded if own CLIs are used. The judged and human outcomes are secondary because of reviewer stake. A complete specification favours the substrate's cascade (little to elicit) and also the naive arms (little to guess): the net direction is not known.

## 13. The separate later experiment: specification completeness (the dial) — not part of E2E-1

One project, the substrate factor kept as in E2E-1 (X versus X+S only), crossed with specification completeness at four levels: one-paragraph intent; intent plus principal rules; criteria for the main flows; complete (E2E-1's specification). The hidden acceptance suite stays complete at every level and is written from the complete specification, with a registered list of the decisions each lower level leaves open. Outcomes: acceptance pass on the complete suite; the assumptions the agent recorded or asked about; defects traceable to an unstated decision. Prediction to test: the substrate's value rises as completeness falls (it forces recording decisions) or falls (it multiplies guesses); the sign is unknown. AX cannot answer it: it varied completeness together with GS content and method in one session each, its upper levels saturated, its later versions were iterated with knowledge of the gaps (demonstration), and its rubric is the treatment's own.
