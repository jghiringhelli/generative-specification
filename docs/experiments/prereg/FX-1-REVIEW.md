## 4. Result of the checker after the review changes

Full run of `npm test` (checker 0.2.0-prototype, 2026-10-05, Windows 11, Node 24.18, Git for Windows 2.54, python 3.11 with pytest 9, about 20 minutes): 42 control variants, determinism, non-interference and 9 unit tests, **53 of 53 passing after one correction**. The correction: the new control X04 (no gate of any kind plus an always-failing lint script) first failed because its own sentinel still named the deleted gate script (E01 `PARTIAL`, a defect of the control, not of the checker); it was fixed and re-run, and passed. Every other new control passed on its first run: the baseline-filtered script credit (X04, X06), the paired controls (X05: a hook that freezes the spec folder no longer earns E07 or E10), the push-stage enforcement (G4), the python good and broken controls (G3, PY1). The pass is evidence that the checker behaves as specified on projects of known properties; as the critics noted, those controls come from one small library written by the checker's author and say nothing about model-written projects.

## 5. What survived that a reader should not miss

1. The headline was mis-stated in revision 1 (both critics found it independently). A "complete substrate" is certifiable only if elements truly sit near 0.99, or if failures cluster by run; "every element at least 90 percent" needs about 0.98.
2. The checker's leniency routes were real (a failing script crediting four elements at once; a frozen spec crediting two) and are now closed by paired controls and baseline filtering, with controls that would have caught them.
3. The study as first written would have spent most of its budget confirming a failure its own prior predicted; the diagnostic stage is the structural answer.
