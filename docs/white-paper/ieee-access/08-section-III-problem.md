## III. PROBLEM FORMALIZATION

### A. The stateless reader as a constraint

A *stateless reader* is an executor that begins each session with no memory of earlier sessions, no institutional context and no channel for a clarifying question. Everything not present in the artifacts is, for it, absent. A language model deployed as a code-generating agent is such a reader: its context resets at the session boundary and it keeps no persistent memory of earlier decisions. A human engineer interprets an underspecified requirement, compensating with memory, inference and shared context; the agent processes what is present. An incomplete description is therefore not deferred until it can be clarified. It is completed immediately, at generation speed, in whatever direction the model's prior favors, which need not be the direction the author intended.

The consequence is drift, the generation-time analogue of architectural erosion [8], [9]. Each session inherits the artifacts of the last, so an incoherence introduced once propagates, which is Lehman's observation that complexity grows unless work is done to reduce it [10]. Larger context windows do not remove the constraint: an unbounded window over an underspecified codebase is an unbounded drift surface, because the model cannot derive intent that was never externalized.

### B. Derivability as the obligation

We call the resulting obligation *derivability*. A system is *derivable* when a stateless reader, given its artifact set alone, can determine what should be built, where, why and to what contracts, without external human context. A specification satisfies the obligation when it makes the correct output derivable from the artifacts alone. "Correct" here includes conformance to behavioral and acceptance obligations and not only well-formedness. A specification can also be internally consistent and wrong, so it faces the same verification burden as the implementation it governs, and a human remains responsible for ratifying that it captures the intention (*ratification*: a person accountable for the project accepts something into force, with a recorded reason).

The obligation has antecedents that GS instantiates for a new reader and does not introduce. Parnas required that design decisions be locatable by inspection [3]; Jackson required the specification to bound the problem or the implementation will fill the gap arbitrarily [7]; Meyer made preconditions, postconditions and invariants explicit [5]. Each assumed a human reader who could still ask. GS restates the obligation for a reader that cannot.

### C. Why disciplines can carry intent (a mechanism hypothesis)

Structural disciplines such as intention-revealing names, interfaces, types, contracts, decision records and ubiquitous language encode human meaning in a form a machine can act on and machine behavior in a form a human can verify; Gordon frames programming as such a linguistic bridge [20]. We hypothesize, and do not test directly, an asymmetry: a model is more reliable at comprehending an explanation of behavior than at reconstructing exact code from raw code, and a codebase carries no record of the reasons behind its decisions. If so, encoding intent as human-conceptual structure inside the repository routes the hard half of the problem through the model's stronger side. Our evidence is indirect: one weak-model observation in which undisciplined code was silently truncated while disciplined units were not (Section VI.G), and the structural effects reported in Section VI. We do not rely on the mechanism for any claim in this paper.

### D. Keeping the reader's context usable: the sentinel

Derivability in principle is worth little if the reader's context is too crowded to use it. A complete specification grows large, and a session that loads all of it spends its attention on irrelevant material. The response is a *sentinel navigational tree*: a hierarchy of specification files in which each node declares its own scope and routes to its children, so a session loads only the slice its task needs. A well-formed tree states architectural identity, standards, prohibitions, tool sequencing and routing; tool sequencing (when to prefer one tool over another) is the most commonly missing. Retrieval over such an authored structure is measured in Section VI.F and in the twin studies of Section VI.G. The structure is authored and not inferred, in contrast to retrieval-augmented generation [28], and it is consistent with reports that long contexts are used unevenly [29].
